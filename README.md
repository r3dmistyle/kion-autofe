# Автоматический поиск признаков против ручного бустинга (KION)

Можно ли заменить ручной feature engineering в ранжировании рекомендаций автоматическим поиском по пространству агрегатов
(«окно × фильтр × связь × агрегация × нормировка»)? Ниже — воспроизводимый пайплайн на датасете KION (МТС), сильный
бейзлайн CatBoost на ручных признаках, AutoFE‑поиск по грамматике из ~9.5 тыс. SQL‑признаков и честное сравнение
на одинаковых кандидатах и разбиении.

## 1. Данные и постановка

**KION**: 5.48 млн просмотров, 962 тыс. пользователей, 15.7 тыс. фильмов/сериалов, 2021‑03‑13…2021‑08‑22.
`interactions(user_id, item_id, last_watch_dt, total_dur, watched_pct)`, `users(age, income, sex, kids_flg)`,
`items(content_type, genres, actors, directors, studios, countries, release_year, age_rating, for_kids, …)`.

Особенности, которые определяют дизайн:
- **Пара user–item встречается ровно один раз** (дата последнего просмотра + суммарная длительность). Повторного
  потребления в данных нет, поэтому «прямые» признаки пары (сколько раз смотрел этот item) вырождаются, а просмотренное
  исключается из кандидатов. Вся персонализация — через **косвенные связи**: жанры, актёры, режиссёры, студии, страны,
  тип контента, декада, возрастной рейтинг и демография.
- Единственный «тип события» — просмотр; его силу задаёт `watched_pct`, поэтому в грамматике есть фильтр `watched_pct ≥ p`.
- Сильный тренд на новинки: популярность за последние дни — очень сильный сигнал.

**Задача**: для пользователя с историей предсказать, что он посмотрит в следующие 7 дней (метка = любое взаимодействие
в целевой неделе). Ранжируем кандидатов, считаем NDCG@10, Recall@10, MAP@10 **относительно всех** просмотров
пользователя в целевой неделе (включая не попавшие в кандидаты), плюс ROC‑AUC и LogLoss на парах.

**Сэмплирование**: случайные N пользователей **со всей их историей** (`--n-users`, сид фиксирован). Основной прогон —
100k пользователей; масштабирование — 25k/50k/100k/200k.

### Разбиение по времени

| фолд | история (признаки, кандидаты) | метки |
|---|---|---|
| train3 | < 2021‑07‑19 | [07‑19, 07‑26) |
| train2 | < 2021‑07‑26 | [07‑26, 08‑02) |
| train | < 2021‑08‑02 | [08‑02, 08‑09) |
| val | < 2021‑08‑09 | [08‑09, 08‑16) |
| test | < 2021‑08‑16 | [08‑16, 08‑23) |

Ранкер учится на трёх train‑неделях (каждая неделя — свои срез, кандидаты, признаки и метки), early stopping, выбор
признаков и гиперпараметров — **только по val**; test используется один раз для итоговых чисел.
Оцениваем «тёплых» пользователей (есть история до среза и есть метка). Холодным отдаём популярное — отдельной строкой.

### Почему нет утечек
1. Каждый признак — SQL‑запрос с `WHERE dt < cutoff`; окна отсчитываются назад от среза.
2. Кандидаты (ItemKNN и популярность) строятся только по истории до среза; item, впервые появившийся после среза,
   кандидатом стать не может.
3. Метка и её `total_dur`/`watched_pct` не используются как признаки.
4. `tests/test_leakage.py` проверяет это механически на синтетике: к данным добавляются тысячи «будущих» событий
   (включая новые items) — кандидаты и **все** проверяемые признаки (ручные + 400 случайных из грамматики) не меняются.
   Там же SQL сверяется с прямым расчётом на pandas. Если заменить `dt < cutoff` на `dt <= cutoff`, тест падает.
5. Известное ограничение самих данных: строка хранит только дату **последнего** просмотра. Если пользователь начал
   смотреть до среза, а досмотрел после, событие целиком попадает в метку и не видно в истории. Это делает задачу
   немного сложнее, но не создаёт утечку.

## 2. Пайплайн

```
events ──► кандидаты (ItemKNN top‑100 ∪ популярное 7д/30д top‑50, без просмотренного; одинаковые для всех моделей)
       ──► base‑признаки (статические атрибуты user/item + скоры и ранги генераторов)
       ──► + набор агрегатов (Hand / Auto / Random)  ──► CatBoost (Logloss; YetiRank как вариант)  ──► top‑10
```

- **Кандидаты**: ItemKNN (косинус по бинарной матрице user×item, 100 соседей на item) top‑100 + популярное за 7 и 30
  дней top‑50, просмотренное исключено. ~140 кандидатов на пользователя; recall кандидатов — потолок любого ранкера.
- **Base** (общие для всех моделей): age, income, sex, kids_flg, content_type, age_rating, for_kids (как
  `cat_features` CatBoost), release_year, knn_score, knn_rank, pop7_rank, pop30_rank.
- **CatBoost**: depth 6, lr 0.05, до 2000 деревьев, early stopping 100 по val; одинаковые гиперпараметры для всех
  наборов признаков; 3 сида. Обучение на T4 (`task_type=GPU`).

### Ручной набор (Hand, 35 признаков)
Писал «как обычно пишут»: активность пользователя за 7/30/all дней, средний watched_pct, давность последнего
просмотра, стаж; популярность item за 7/14/30/all, доля в популярности, досмотры, свежесть, тренд pop7/pop30, «возраст»
item на платформе; доля жанра/страны/студии/типа контента/рейтинга/декады в истории пользователя, число просмотров с
теми же актёрами и режиссёром, lift жанра; популярность item внутри возрастной/гендерной/доходной группы и группы
«с детьми»; разница года выпуска с типичным для пользователя. Полный список — `HAND` в `src/features.py`.

### Грамматика признаков (Auto)
Признак = `ключ | фильтр | окно | агрегация | нормировка | свёртка` и компилируется в один SQL‑запрос DuckDB:

| измерение | значения |
|---|---|
| ключ (связь) | `user`, `item`, `ui:<атрибут item>` (история пользователя по значению атрибута: genre, actor, director, studio, country, content_type, age_rating, decade), `iu:<атрибут user>` (история item внутри группы пользователя: age, income, sex, kids_flg) |
| фильтр | все события / `watched_pct ≥ 10 / 50 / 90` |
| окно | 1, 3, 7, 14, 21, 30, 60, 90 дней, вся история, экспоненциальное затухание с полупериодом 3/7/14/30/90 дней |
| агрегация | `cnt` (число просмотров), `dur` (время), `pct` (средний watched_pct), `rec` (1/дней с последнего) |
| нормировка | `raw`, `share` (доля от итога пользователя/группы), `lift` (доля / глобальная доля) |
| свёртка по значениям item | `max`, `mean`, `sum` (для многозначных атрибутов) |

Итого **9 476** признаков в 784 SQL‑группах (одна группа = ключ × фильтр × окно, один запрос даёт до 22 колонок).
Например, `ui:genre|f50|d14|cnt|share|max` — максимальная по жанрам item доля досмотренных (≥50%) просмотров этого
жанра у пользователя за 14 дней.

### Поиск (только по val)
1. **Скрининг всей грамматики**: группы перемешиваются и собираются в чанки по ~200 признаков; на каждом чанке быстрый
   CatBoost (300 деревьев, lr 0.1) на base + чанк, признаку достаётся его importance. Ничего из грамматики не
   сохраняется на диск — признаки считаются SQL на лету.
2. **Пул**: top‑100 по importance без почти‑дубликатов (|corr| > 0.95).
3. **Жадный forward‑отбор** в порядке importance: признак остаётся, если val NDCG@10 вырос больше чем на ε = 5·10⁻⁴.
4. **Локальные мутации**: случайный выбранный признак заменяется соседом по грамматике (другое окно/фильтр/агрегация/
   нормировка/свёртка); замена принимается при приросте > ε. Это прямой ответ на вопрос «почему 7 дней, а не 10».

Контроль: **Random** — столько же признаков, сколько в Hand, случайно из той же грамматики (3 выборки).

## Как воспроизвести

```bash
python3 -m venv .venv && .venv/bin/pip install -r requirements.txt
.venv/bin/python tests/test_leakage.py            # утечки + сверка SQL с pandas
.venv/bin/python src/ranker.py                    # self-check метрик
.venv/bin/python src/experiments.py --n-users 25000 --device cpu --seeds 1 --train-weeks 1 --pool 10 --mut-fits 3  # быстрый прогон
```

Полный прогон — `colab.ipynb` на T4 (датасет скачивается автоматически):

```bash
python src/experiments.py --n-users 100000 --device gpu --steps e0,hand,search,auto,windows
python src/experiments.py --n-users 50000 --device gpu --seeds 1 --steps e0,hand,auto --search-from results/n100000
python src/experiments.py --steps report    # results/summary.md и графики
```

Структура: `src/prep.py` — сэмпл, таблицы DuckDB, фолды, кандидаты; `src/features.py` — грамматика → SQL, ручной
набор; `src/ranker.py` — CatBoost и метрики; `src/search.py` — AutoFE; `src/experiments.py` — эксперименты и отчёт;
`results/` — JSON со всеми прогонами и графики.
